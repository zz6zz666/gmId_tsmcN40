# TSMC N40 Mathematica Lookup API

This directory contains `tsmcN40_lookup.wl`, a Mathematica API for the HDF5
lookup tables generated by `extract_new.py`.

The table axes are:

```text
(L, VGS, VDS, VSB)
```

The API keeps the five usage modes distinct:

1. `lookup`: direct lookup of a stored variable.
2. `lookup`: direct lookup of a derived ratio.
3. `lookup`: cross-lookup of one ratio against another ratio.
4. `lookupVGS`: recover VGS when the source voltage is known.
5. `lookupVGS`: recover VGS when the source voltage is unknown.

## Load The Table

```wl
Get["mathematica/tsmcN40_lookup.wl"];
data = LoadTsmcN40["D:\\tsmcN40_lookup\\nch_tt.h5"];
```

The selective form loads only named datasets:

```wl
data = LoadTsmcN40["D:\\tsmcN40_lookup\\nch_tt.h5",
  {"L", "VGS", "VDS", "VSB", "GM", "ID", "CGG", "W"}];
```

Table values can also be accessed directly:

```wl
data["VDSAT"]
data["GM"] / data["ID"]
data["GM"] / data["CGG"]
```

## Common Names

The table axes are `L`, `VGS`, `VDS`, and `VSB`. The scalar metadata fields
include `CORNER`, `DEVICE`, `INFO`, `TEMP`, `W`, and `NFING`.

The stored electrical variables are:

```text
ID   VT   IGD  IGS  GM   GMB  GDS  CGG  CGS  CSG
CGD  CDG  CGB  CDD  CSS  VDSAT
```

The stored noise variables are:

```text
STH  SFL
```

Derived names use `NUMERATOR_DENOMINATOR` syntax. The numerator must be a
stored 4-D variable, and the denominator may be another stored 4-D variable
or `W`:

```text
GM_ID    = GM / ID
GM_CGG   = GM / CGG
GM_CGS   = GM / CGS
GM_GDS   = GM / GDS
GMB_ID   = GMB / ID
ID_W     = ID / W
CGG_W    = CGG / W
CGS_W    = CGS / W
CGD_W    = CGD / W
CDD_W    = CDD / W
CSS_W    = CSS / W
```

The ratio syntax is generic; the examples above are the commonly used names,
not an exhaustive list. For example, `GDS_ID`, `GM_VT`, and `CGG_CGD` follow
the same rule when the corresponding stored variables exist.

Parameter names are case-insensitive. Results outside the table domain are
returned as `Indeterminate`.

## Mode 1: Stored Variable Lookup

Mode 1 evaluates a stored four-dimensional table at `L`, `VGS`, `VDS`, and
`VSB`. The coordinate arguments may appear in any order. Defaults are:

```text
L   = Min[data["L"]]
VGS = data["VGS"]
VDS = Max[data["VDS"]] / 2
VSB = 0
```

```wl
lookup[data, "ID", "L", .04, "VGS", .6, "VDS", .7, "VSB", 0.]
lookup[data, "VDSAT", "L", .04, "VGS", .6, "VDS", .7, "VSB", 0.]
```

Lists retain Cartesian semantics. The result dimensions follow
`{L, VGS, VDS, VSB}`, omitting dimensions whose inputs are scalar.

```wl
idGrid = lookup[data, "ID",
  "L", {.04, .06}, "VGS", {.5, .6}, "VDS", .7, "VSB", 0.];
Dimensions[idGrid]                         (* {2, 2} *)
```

## Mode 2: Derived Ratio Lookup

Mode 2 uses the same coordinate and batching rules as mode 1, but computes a
ratio from the selected numerator and denominator tables only at the required
interpolation corners.

```wl
idPerWidth = lookup[data, "ID_W", "VGS", .6, "VDS", .7, "L", .04]
```

## Mode 3: Cross-Lookup

Mode 3 finds the VGS point where an input ratio reaches the requested target,
then evaluates one or more output ratios at that same recovered VGS. The
syntax puts the output variable first and the input variable second:

```wl
lookup[data, "GM_CGG", "GM_ID", {8., 10., 12.},
  "L", .04, "VDS", .7, "VSB", 0.]
```

The final one-dimensional interpolation defaults to `"pchip"`. The accepted
methods are `"pchip"`, `"linear"`, and `"cubic"`:

```wl
lookup[data, "GM_CGG", "GM_ID", {8., 10., 12.},
  "VDS", .7, "METHOD", "linear"]
```

The multidimensional table interpolation remains linear.

### Multiple Outputs

Several output ratios can be evaluated from the same recovered VGS values:

```wl
{gain, ftRatio, currentDensity} =
  lookup[data, {"GM_GDS", "GM_CGG", "ID_W"},
    "GM_ID", {8., 10., 12.}, "L", {.04, .06}, "VDS", .7, "VSB", 0.];
```

The return value is a list in the same order as the output-name list. Each
array has dimensions `{L, VDS, VSB, target}` after singleton squeezing.

## Mode 4: lookupVGS With Known Source Voltage

This mode recovers VGS from one inversion variable while `VDS` and `VSB` are
known. The inversion variable is exactly one of `GM_ID` or `ID_W`; the function
always returns VGS, never multiple physical output variables.

```wl
lookupVGS[data, "GM_ID", 15., "L", .04, "VDS", .7, "VSB", 0.]
lookupVGS[data, "ID_W", 1.*^-4, "L", .04, "VDS", .7, "VSB", 0.]
```

Target vectors are useful when sampling one fixed bias path:

```wl
lookupVGS[data, "GM_ID", {10., 12., 15.},
  "L", .04, "VDS", .7, "VSB", 0.]
```

The implementation also supports Cartesian vectors for `L`, `VDS`, `VSB`,
and the target. The result dimensions are:

```text
{L, VDS, VSB, target}
```

For example:

```wl
vgsGrid = lookupVGS[data, "GM_ID", {10., 12., 15.},
  "L", {.04, .06}, "VDS", {.5, .7}, "VSB", 0.];
Dimensions[vgsGrid]                         (* {2, 2, 3} *)
```

`"pchip"`, `"linear"`, and `"cubic"` apply to the final one-dimensional
inversion.

## Mode 5: lookupVGS With Unknown Source Voltage

This mode is for a source node whose voltage is not known directly, such as a
tail node or an internal cascode node. Supply `VDB` and `VGB`; the function
constructs the source-bias path:

```text
VGS = VGB - VSB
VDS = VDB - VSB
```

```wl
lookupVGS[data, "GM_ID", 10.,
  "VDB", .6, "VGB", 1., "L", .04]
```

The mode 5 call accepts scalar `VDB`, `VGB`, and `L`, while the inversion target
may be a vector:

```wl
lookupVGS[data, "GM_ID", {10., 12., 15.},
  "VDB", .6, "VGB", 1., "L", .04]
```

Mode 5 has a different path geometry from mode 4 and uses a separate path
sampler. It is not combined with the ordinary fixed-source Cartesian batch
kernel. Independent mode 5 paths used through `Map` or `MapThread` are sampled
in one point batch.

The source-bias path sampling step is derived from the first two `VGS` axis
entries.

## Vector Inputs And Output Dimensions

This table lists every public vector input. Cartesian inputs form all
combinations. The `VGS` vector in mode 3 is the curve sampling axis and is not
returned as a result dimension.

| Mode | Vector-capable inputs | Combination rule | Result dimensions |
| --- | --- | --- | --- |
| `lookup` mode 1 | `L`, `VGS`, `VDS`, `VSB` | Cartesian | `{L,VGS,VDS,VSB}` |
| `lookup` mode 2 | `L`, `VGS`, `VDS`, `VSB` | Cartesian | `{L,VGS,VDS,VSB}` |
| `lookup` mode 3 | input target, `L`, `VDS`, `VSB` | Cartesian | `{L,VDS,VSB,target}` |
| `lookup` mode 3 | `VGS` | sampling axis | no extra result dimension |
| `lookupVGS` mode 4 | target, `L`, `VDS`, `VSB` | Cartesian | `{L,VDS,VSB,target}` |
| `lookupVGS` mode 5 | target | vector | `{target}` |
| `lookupVGS` mode 5 | `VDB`, `VGB`, `L` | direct vectors | use `Map`/`MapThread` |

Dimensions belonging to scalar inputs are omitted. For example:

```wl
lookup[data, "GM_ID", "L", {.04, .06}, "VGS", {.5, .6},
  "VDS", {.5, .7}, "VSB", {0., .1}]
(* Dimensions: {2, 2, 2, 2} *)

lookup[data, "GM_CGG", "GM_ID", {8., 10., 12.},
  "L", {.04, .06}, "VDS", {.5, .7}, "VSB", {0., .1},
  "VGS", data["VGS"]]
(* Dimensions: {2, 2, 2, 3} *)

lookupVGS[data, "GM_ID", {10., 12., 15.},
  "L", {.04, .06}, "VDS", {.5, .7}, "VSB", {0., .1}]
(* Dimensions: {2, 2, 2, 3} *)
```

## Output Order With Map And MapThread

When native vectors are combined with `Map` or `MapThread`, there are two
levels of ordering:

1. The outer level follows the mapped calls. `Map` preserves its input order;
   `MapThread` preserves paired positions.
2. Each mapped result follows the Cartesian dimensions of its own call:
   `{L,VGS,VDS,VSB}` for direct lookup, `{L,VDS,VSB,target}` for cross-lookup,
   and `{L,VDS,VSB,target}` for known-source `lookupVGS`.

```wl
result = Map[
  lookupVGS[data, "GM_ID", {10., 12.}, "L", #, "VDS", {.5, .7}] &,
  {.04, .06}
];
Dimensions[result]                         (* {2, 2, 2} *)
```

Here the dimensions mean:

```text
result[[outer, vds, target]]
```

The outer index follows `{.04, .06}`, the VDS index follows `{.5, .7}`, and
the target index follows `{10., 12.}`.

With `MapThread`, the outer position is paired, while vectors inside each
paired item remain Cartesian:

```wl
result = MapThread[
  lookupVGS[data, "GM_ID", #1, "L", #2, "VDS", #3] &,
  {
    {{10., 12.}, {11., 15.}},
    {{.04, .06}, {.08, .1}},
    {{.5, .7}, {.6, .8}}
  }
];
Dimensions[result]                         (* {2, 2, 2, 2} *)
```

`result[[1]]` is the first paired item and `result[[2]]` is the second. Each
inner result has dimensions `{L,VDS,target}`. Pairing is controlled by the
outer `MapThread`; ordinary vectors passed inside one lookup call remain
Cartesian.

## Map And MapThread

Map optimization rules for `lookup` and `lookupVGS` are installed when the file
is loaded. They batch independent calls without changing the behavior of other
Mathematica functions.

### Map Over Bias Values

```wl
lookup[data, "GM_GDS", "GM_ID", #,
    "L", .04, "VDS", .7, "VSB", 0.] & /@
  {8., 10., 12.}
```

For `lookupVGS`, the same pattern batches independent VGS recovery calls:

```wl
lookupVGS[data, "GM_ID", 15., "L", #, "VDS", .7, "VSB", 0.] & /@
  {.04, .06, .08}
```

Unknown-source paths are batched as separate path rows:

```wl
MapThread[
  lookupVGS[data, "GM_ID", {10., 12.},
    "VDB", #1, "VGB", #2, "L", #3] &,
  {{.6, .7}, {1., 1.05}, {.04, .06}}
]
```

### MapThread By Position

```wl
MapThread[
  lookup[data, "GM_GDS", "GM_ID", #1, "L", #2, "VDS", #3] &,
  {{8., 10., 12.}, {.04, .06, .08}, {.5, .7, .9}}
]
```

`MapThread` lists are paired by position. Lists contained inside one paired
item remain ordinary lookup vectors and therefore retain Cartesian semantics:

```wl
MapThread[
  lookupVGS[data, "GM_ID", #1, "L", #2, "VDS", #3] &,
  {
    {{10., 12.}, {11., 15.}},
    {{.04, .06}, {.08, .1}},
    {{.5, .7}, {.6, .8}}
  }
]
```

Each outer result in this example has dimensions `{L, VDS, target}`.

### Map Over Output Variables

Multiple independent output-variable calls are equivalent in value and result
order to one explicit multi-output lookup when the other arguments are shared:

```wl
Map[
  lookup[data, #, "GM_ID", {8., 10., 12.}, "L", .04, "VDS", .7] &,
  {"GM_CGG", "GM_GDS", "ID_W"}
]
```

This is equivalent to:

```wl
lookup[data, {"GM_CGG", "GM_GDS", "ID_W"},
  "GM_ID", {8., 10., 12.}, "L", .04, "VDS", .7]
```

The latter form makes the multi-output intent explicit. `lookupVGS` is not a
multi-output function: mapping it batches several VGS queries, but each query
still returns only VGS.

### Disabling The Rules

```wl
DisableTsmcN40MapOptimization[];
EnableTsmcN40MapOptimization[];
```

When a Map expression is not recognized or cannot be safely batched, it falls
back to ordinary element-by-element evaluation.

## Lower-Level Helpers

`N40Interpolant` creates a reusable four-dimensional linear interpolant:

```wl
f = N40Interpolant[data, "GM_ID"];
```

`SliceVGS` returns `{VGS,value}` samples for plotting or custom analysis. It
uses the same four-dimensional linear lookup as mode 1:

```wl
curve = SliceVGS[data, "GM_ID", .04, .7, 0.];
ListLinePlot[curve, AxesLabel -> {"VGS (V)", "GM/ID"}]
```

`METHOD` controls only the final one-dimensional inversion in cross-lookup and
`lookupVGS`; four-dimensional table interpolation is always linear.
